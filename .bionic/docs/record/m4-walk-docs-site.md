# M4 docs site walk

A first-look pass through the running `mambo-power` docs site (`mkdocs serve`, mkdocs-material), driven with a real browser via `playwright-cli`, starting from the home page and following the nav, a scroll-through of the new manual page, and search the way a visitor would. Screenshots are in `walk-m4/`, numbered in the order I took them.

## Home page

`walk-m4/01-home.png`. Same clean landing page shape as before: pitch paragraph, runnable snippet, status callout, three-principles section, system-context diagram, a "where to go next" table, and a roadmap table at the bottom.

The status callout reads: wave M1 and M2 are merged, and "Wave M3 ... is in progress on its own wave branch, with everything below shipped" — DC-OPF with LMPs, N-1 screening, both exposed through `jobs.run`. It doesn't say one word about a nodal market, LMP-based settlement, or elastic demand. The "where to go next" table lists rows for DC-OPF and N-1 screening but has no row pointing at the new Nodal-market manual page at all — a visitor scanning that table for "how do I clear a market" would find nothing. And the roadmap table at the very bottom still lists "M4-M7: Markets: nodal LMP, zonal + redispatch, multi-period with storage, agent-based bidding" as **planned**. But the site I'm actually looking at has a full nodal-market manual page, a `mambo_power.market` API reference module, and a ninth runnable example — all live, one click away in the nav. So the home page's own narrative of "what's done" is stale in two directions at once: it undersells M3 (calling it "in progress" when its content reads as finished) and it doesn't acknowledge M4 exists at all. A visitor landing here first would have no idea nodal-market clearing is in the package.

Every page throws the same one console error on load: a 404 fetching `https://api.github.com/repos/mambo10005/mambo-power/releases/latest` — the header's repo-star/fork widget failing to reach GitHub, presumably because this sandbox has no outbound network access. Cosmetically harmless (stars/forks just show "0 0"), consistent across every page I visited.

## Manual → Nodal market

I found the new page via the Manual dropdown's sub-nav, which now lists "Nodal market" between "N-1 screening" and "Results" (`walk-m4/02-manual-market-top.png`). The page is dense, well-structured technical writing in the same voice as the rest of the manual: an entry-point table, the elastic-demand LP formulation, the double-counting and convexity subtleties, the LMP/settlement math, a price-taker reduction, an "oracle & fixtures" section explaining how bid data is derived rather than invented, an errors section, a runnable "using it" snippet, and a Jobs API tie-in.

Math rendering is genuinely good here, in contrast to what I'd expect from a first look — I checked closely because diagram/formula rendering is exactly the kind of thing that fails silently. The welfare LP (`walk-m4/03-manual-market-scenario-elastic.png`) renders as a proper multi-line equation with real summation signs, subscripts, and a `s.t.` constraint, not raw LaTeX source. The LMP decomposition formula (`walk-m4/04-manual-market-doublecount-convexity.png`) is more elaborate still — it uses braces under the summed terms labeled "energy" and "congestion" — and it renders correctly too, crisp and readable. I didn't find a single instance of unprocessed `\(...\)` or `\[...\]` source leaking onto the page anywhere in this manual page, which was the dominant defect a prior look at this site found on the OPF and N-1 pages.

The prose is candid about a known rough edge: it says elastic demand modeled as a genuine quadratic cost attached directly to a load "reproducibly fails to converge" in the pandapower oracle used for parity testing, for reasons the author explicitly says weren't worth root-causing this wave, and points a reader at the test file that documents the bug (`walk-m4/06-manual-market-errors-using.png`). That's an unusually honest thing to see spelled out in public-facing docs rather than swept under the rug.

One thing did stand out as an internal-process leak into reader-facing prose: partway down the page, a sentence names a specific unit-test file and then, before the sentence's parenthetical, tacks on a short internal test-tracking code (a two-letter prefix, a hyphen, and a digit — the kind of shorthand a team uses in its own planning documents) as if the reader is expected to recognize it. A reader with no access to this project's internal planning artifacts has no way to resolve what that code refers to; it reads as leaked internal shorthand rather than documentation.

The "using it" code sample (`walk-m4/07-manual-market-using-code.png`) is syntax-highlighted and, unlike a code block I checked elsewhere on this same page's worked example (see below), didn't visibly clip any lines in the viewport width I used. The Jobs API section at the bottom (`walk-m4/08-manual-market-jobsapi.png`) shows an actual command-and-output pair (`Optimal` / `20.0 45.0 700.0`) presented as if it's real output from running the snippet above it, and closes by naming `market.nodal` as a registered `jobs` kind with a link into the jobs manual's failure-shape section.

## API reference → mambo_power.market

`walk-m4/09-api-market-top.png` through `walk-m4/12-api-source-expanded.png`. Full mkdocstrings-generated reference: module doc, `MarketNodalOptions`, `NonConcaveBidError`/`NonConvexCostError`, and `solve_nodal`, with a nested `mambo_power.market.nodal` submodule page below it. Clicking "Source code in ..." expanded cleanly to show the real implementation with line numbers, same as the rest of the API reference.

Two things repeat from what I'd expect based on prior conventions on this site, both present here again:

- Every "Source code in ..." path shows Windows backslashes (`src\mambo_power\market\nodal.py`) — almost certainly a local-build artifact of running on Windows rather than something that'd show up in a Linux CI-published build, but it's what's actually rendered.
- The module docstrings leak internal wave-planning shorthand into public API documentation, more than once. The top-level `mambo_power.market` docstring says "wave M4 W4" twice in two short paragraphs. The nested `mambo_power.market.nodal` module docstring goes further: it says "spec design item 5; wave M4 W4" in its first sentence, and later, describing the settlement identity, cites "the identity proved in `record/m4-research.md §4.1`" — a literal path into what reads like an internal research/scratch document, presented as if a reader could open it. None of `wave M4 W4`, the spec-item reference, or that file path mean anything to someone reading only the published API docs.

The same internal test-tracking code I flagged on the manual page shows up again, verbatim, inside the *example script's own module docstring* — which I confirmed is embedded directly into the rendered Examples page (see below), so it's not just a source-comment a reader would never see; it's on the public page.

## Design → Architecture

`walk-m4/13-design-architecture-top.png`. The component diagram now shows a `market` box (labeled "solve_nodal (nodal LMP clearing)") wired into `opf`, sitting inside a "Shipped (M1-M4)" group, with a separate "Later waves" group showing `market.zonal/multiperiod/agents (M5-M7)` and the pandapower/PyPSA/PSS-E/CSV bundle for M8. Content-wise this matches what the manual and API pages describe. The ownership table further down has a row for "LMP / congestion rent" owned by `market.nodal (M4)`, consumed by "zonal comparison, multiperiod, agents."

I noticed the second diagram on this page — the "Data flow of one solve" sequence diagram (`walk-m4/19b-design-dataflow-sequence.png`) — still only shows the old DC power-flow path (caller → `io.matpower` → `model.Network` → `numerics.NetworkArrays` → `pf.dc_solve` → `results.from_arrays`). There's no sequence diagram anywhere on this page for a `market.solve_nodal` call. Not necessarily wrong — the page doesn't claim to cover every entry point — but a reader who came to this page specifically to understand how a market-clearing call flows through the modules won't find it modeled, only the component-level box-and-arrow view.

The more interesting thing I ran into on this page was in trying to double check the diagrams weren't silently broken the way a previous look at this site found mermaid diagrams to be lazily/blank on fresh load: I confirmed via direct DOM inspection (`document.querySelectorAll('.mermaid')`, checking `.children.length` and `.innerHTML`) that both mermaid containers on this page are completely empty — zero child nodes, no `svg`, no `data-processed` marker mermaid.js normally leaves after rendering — at every point I checked, including immediately before and after taking a screenshot within the same script. And yet every screenshot I took shows the diagrams fully and correctly rendered, readable text and all, surviving a forced scroll-repaint and a full page reload. I could not find where the visible pixels are actually coming from: no `<iframe>`, no shadow root, no `<img>`/background-image on the container, and `document.elementFromPoint()` at a coordinate squarely inside the visible diagram returns the same empty `<div class="mermaid">`. I don't have an explanation for this — it may be a Chromium/CDP paint-vs-DOM quirk specific to how this browser automation captures the page rather than anything wrong with the site itself, since a human looking at this in an ordinary browser window would see a correctly rendered diagram either way. I'm flagging it because it's the single strangest thing I ran into on this walk, not because I believe it reflects a bug a real visitor would ever notice.

## Examples → 09. Nodal market

`walk-m4/20-examples-09-nodal-market.png`, `walk-m4/21-examples-09-output.png`. The new example is embedded the same way as the rest of the gallery (the page states the code shown is the same bytes CI runs). The docstring gives a plain-English tour: a hand-built 2-bus network, a cheap slack generator and an expensive one behind a rated branch, one load with a two-segment piecewise-linear bid and one fixed unbid load, and a closing note about the settlement identity.

The same code-block clipping I'd expect from this site's `<pre>` styling is present here too: long docstring lines ("...the same fixtu[re-free style]...", "...the identical [decomposition]...") are cut off at the right edge of the block with no scrollbar or wrap, so a reader can't see the rest of the sentence without viewing source. This looks like the same site-wide behavior rather than anything specific to this page.

## Manual → Results (checking for the new result type)

I expected `MarketNodalResult` to get at least a mention on the general Results manual page, since it's a new result-shape the package returns. It doesn't — I checked the rendered page text directly (`document.body.innerText`) and the string isn't there at all (`walk-m4/22-manual-results-top.png`). The table of contents only has the pre-existing sections: shape of a power-flow result, `ResultProvenance`, `BusResult`, `BranchResult`, `GenResult`, `DcPowerFlowResult`/`AcPowerFlowResult`, JSON round-trip, `to_arrays()`, building results from arrays. `MarketNodalResult` is documented on the Nodal-market manual page and in the API reference, but a reader who goes to "Manual → Results" specifically to see what result shapes exist would come away thinking the market result doesn't exist.

## Search

Tried searching `NonConcaveBidError` first by filling the search box programmatically — that didn't actually trigger the search index (the box kept showing "Type to start searching" even after a second and a half of waiting), which turned out to be a quirk of how I drove it rather than the site: switching to real keystrokes and searching `solve_nodal` instead worked immediately. It surfaced "3 matching documents," with the top hit showing the exact function signature and a syntax-highlighted excerpt of the real implementation with `solve_nodal` highlighted in place (`walk-m4/24-search-solve_nodal.png`). Clicking through landed exactly on `mambo_power.market.solve_nodal` with the term highlighted on the page and a `?h=solve_nodal` query param carrying the highlight (`walk-m4/25-search-landed.png`). The search index clearly reaches into the new module's docstrings and source, same as it does for older modules.

## Overall

The new nodal-market content itself is thorough, technically confident writing — the elastic-demand formulation, the double-counting and convexity discussion, the settlement identity, the honest note about a pandapower convergence quirk the author chose not to chase down, and a worked example that ties dispatch, LMPs, and settlement together. The math renders cleanly on this page, which is a real improvement over what I'd expect given this site's history with formula rendering. What I'd most want someone to look at: the home page is now stale in two directions (undersells the previous wave, says nothing about this one, and its own roadmap table contradicts what's one click away in the nav); internal wave/spec-planning shorthand and at least one internal file path leak into public docstrings and a public example's module docstring in a few places; the Results manual page doesn't mention the new market result type at all; and — a smaller, stranger thing — I could not explain why a direct DOM query on the architecture page's mermaid diagrams reports them as completely empty while every screenshot shows them rendered correctly.
